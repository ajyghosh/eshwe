**FLOW-01 — A stored paid order's status page depends on a fresh Razorpay response.** `functions/index.js:400` reads and authorizes the existing order, but calls `commerce.reconcile()` before returning it. `functions/commerce.js:173` fetches provider payments even for an already captured, committed and dispatched order. In the probe, a provider outage produces HTTP 503 with no order payload despite the database retaining the paid order. `src/components/order-status-page.tsx:22` shows the error, and its catch path does not schedule an automatic retry. Customers returning through the payment/status link cannot see confirmation there. The separate order-history receipt path still exists; this is not a claim that every receipt route fails.

Fix: return the authorized, stored order with an explicit refresh-unavailable state when reconciliation fails; preserve all payment/reservation safety checks and disable any action requiring fresh provider evidence. Retry transient refresh failures with bounded backoff. Acceptance: a paid customer sees the stored confirmation during a simulated provider outage; an unresolved payment is clearly unresolved and cannot trigger a second payment or unsafe stock release.

**FLOW-02 — A completed checkout can block the customer's next purchase.** `src/lib/checkout.ts:18` reuses the local pending checkout key. If a customer closes the tab before the status page mounts and payment completes through a webhook, that key remains. The recovery banner checks server state but does not clear the terminal key (`src/components/checkout-recovery-banner.tsx:13`). The probe completes payment outside the status page, then starts another purchase: the same bag returns the old paid order; a changed bag returns HTTP 409. The banner hides its recovery link for a paid order without an attention flag, making recovery difficult. Visiting the old order's status page can clear the key, but customers should not need that workaround.

Fix: reconcile the pending reference's lifecycle centrally. Clear only a matching, conclusively terminal checkout before creating a fresh key; never clear an unrelated active checkout while viewing an older receipt. Preserve keys for unresolved payments. Acceptance: close the checkout tab, complete payment through the webhook, return and purchase the same or different product successfully, with exactly one new order. Repeat after cancellation/expiry and while another checkout remains active.

**FLOW-03 — Failed Admin saves can break live images.** `src/components/owner-category-manager.tsx:121` deletes the old image before saving the new category metadata at line 143. The actual handler probe deletes the old path and then encounters a failed database save, leaving the published reference pointing at a deleted object. `src/components/owner-homepage-manager.tsx:72` similarly deletes the hero before later carousel validation and the metadata save at line 141. The homepage probe rejects an invalid one-slide carousel after deleting the old hero. Launch-image changes and category deletion have the same ordering pattern.

Fix: validate first; upload replacements; commit the new metadata; only then clean up assets no longer referenced. On failure, retain published assets and remove only newly uploaded, unreferenced files. Account for concurrent editors before deleting shared paths. Acceptance: inject validation, upload and database failures in each manager and verify every published image remains readable; verify a successful edit publishes its replacement before cleanup.

**FLOW-04 — The reconciliation worker can repeatedly skip later orders.** `functions/index.js:439` reads at most 100 expired reservations and 100 attention-required orders, without pagination or a rotating retry schedule. Persistent failures can occupy the same query window indefinitely. With 101 attention-required orders and persistent failures on the first 100, two scheduler runs made 200 attempts on the same 100 orders and never attempted order 101. This reproduction uses a deterministic in-memory query; production query ordering was not separately exercised. The absence of traversal/rotation is visible in the source.

Fix: use bounded, paginated processing and durable retry scheduling/backoff so persistent failures cannot monopolize every run. Add an alert for old unresolved orders. Acceptance: with over 100 persistent exceptions, every eligible order eventually receives an attempt; overlapping runs remain safe and provider failures do not release uncertain stock.

**FLOW-05 — Checkout accepts invalid delivery PINs.** `functions/index.js:588` checks only that the PIN is a non-empty string. The web address builder (`src/components/payment-page.tsx:870`) and PWA builder (`src/components/mobile-app-pages.tsx:3403`) also only require non-empty address fields. The actual checkout API accepted `abc`, reserved inventory and returned `canPay: true`.

Fix: validate the intended country's postal format on both client and server, and check actual delivery coverage before allowing payment. State/city/PIN consistency and unsupported delivery regions need a defined handling path. Acceptance: malformed PINs are rejected before any reservation/provider order is created; supported and unsupported delivery examples produce the intended result on web and PWA. Separately confirm the current business choice: `functions/commerce.js:76` always charges zero shipping/packaging. Free shipping may be intentional, but coverage and charges must match fulfilment capabilities.

An open tab can still run the previous build while its cached assets disappear. Whether a subsequent route/chunk request fails depends on deployment retention and cache state; this was **not reproduced across two deployed versions** in this pass. Test a real installed version upgrading while a customer has an address draft and an active payment. Provide a safe update/reload flow that preserves the checkout reference and user input; avoid forced reloads during payment.
